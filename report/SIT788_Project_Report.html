1. Introduction and Bot Purpose

Ink AI is an intelligent multimodal recommendation bot developed using Microsoft Azure AI services. The system is designed to assist users in conceptualising, refining, and visualising personalised tattoo designs through natural conversation. The bot accepts three distinct forms of user input — typed text, recorded voice, and uploaded reference images — and responds with curated style recommendations, detailed design suggestions, and AI-generated concept artwork. All three input modalities can be used interchangeably within a single conversation session, fulfilling the multimodal interaction requirement of this task.

The primary purpose of the bot is to replicate the consultation experience a client would have with a professional tattoo artist. A significant proportion of individuals seeking tattoos find it difficult to articulate their vision clearly, particularly when working with an artist for the first time. They may have a general aesthetic preference but lack the vocabulary to describe specific styles, placement considerations, or cultural references. Ink AI addresses this challenge by using conversational AI to iteratively extract the user's preferences through natural dialogue, refine those preferences over multiple conversation turns, suggest appropriate artistic styles with detailed justification, and ultimately generate a visual concept image that the user can present to a tattoo artist as a reference.

1.1 Target Users

The bot is designed for individuals who are considering getting a tattoo but are uncertain about the design, style, placement, or cultural significance of what they want. It is equally useful for experienced tattoo enthusiasts who wish to explore new artistic styles, generate quick concept references before an artist consultation, or review how different design elements would work together in a single composition.

1.2 Recommendation Scope

The bot provides recommendations across a comprehensive range of established tattoo styles. These include Japanese irezumi, fine line single-needle, geometric dotwork, blackwork, watercolour, photorealistic black and grey, tribal, neo-traditional, and mandala. For each recommendation, the bot provides guidance on the specific design elements appropriate to that style, the recommended placement on the body, the typical size range, the colour palette characteristics, and where relevant, the cultural or symbolic significance of the chosen motifs. The bot also considers practical constraints such as how a design wraps around curved anatomy, how fine detail will age over time, and how multiple tattoo elements can be composed coherently across a larger body area such as a sleeve or back piece.

2. Dataset and Knowledge Base

The recommendation engine in Ink AI operates on two distinct and complementary layers of data. Together, these layers provide both broad domain expertise and personalised, user-specific knowledge that improves with each interaction.

2.1 Foundation Knowledge via GPT-4o Pre-trained Corpus

The primary knowledge base for tattoo style recommendations is the implicit dataset embedded within the GPT-4o large language model, developed by OpenAI and accessed through the Microsoft Azure OpenAI Service. This model was trained on an extensive corpus of text and image-paired data encompassing professional tattoo artist publications, tattoo culture documentation, design principle literature, anatomical placement guides, colour theory resources, and cultural anthropology sources covering the symbolic meanings of motifs across Japanese, Polynesian, Celtic, and other tattoo traditions. The breadth of this pre-trained dataset allows the bot to reason about highly specific stylistic combinations — for example, explaining why a fine-line single-needle design is unsuitable for areas of high skin elasticity, or how the visual weight of a traditional Japanese background fill affects readability at distance.

This foundation dataset is not static data that was manually curated for this project. Rather, it represents the accumulated knowledge embedded in GPT-4o through its training process, accessed and applied dynamically based on each user's unique input. The Azure OpenAI API provides the interface through which this knowledge is queried in a structured, conversational format.

2.2 Dynamic User Preference Dataset (PostgreSQL)

The second layer of the dataset is a per-user dynamic knowledge base stored in a PostgreSQL relational database that runs as part of the Docker Compose deployment. This dataset grows with each user interaction and contains structured records of each individual's aesthetic preferences as extracted from their conversation history.

After every assistant response, the system automatically runs a background extraction task. This task sends the full conversation to GPT-4o with a structured extraction prompt, instructing the model to return a JSON object containing identified tattoo preferences. The extracted fields include preferred tattoo styles (for example, Japanese irezumi or fine line botanical), themes and subjects of interest (for example, nature, mythology, or geometric patterns), colour preferences (for example, black and grey, soft pastels, or bold vibrant fills), and preferred placement areas (for example, forearm, sleeve, or back piece).

These extracted values are stored in the user_preferences table in PostgreSQL and are retrieved and injected into the system prompt at the start of every subsequent API call. This means that by the second conversation a user has with the bot, the system already knows their established preferences and can provide recommendations that build on prior sessions without requiring the user to repeat themselves. Over multiple conversations, the preference dataset becomes increasingly refined and personalised, enabling the bot to function as a genuine long-term creative collaborator rather than a generic question-and-answer tool.

2.3 Conversation History as Contextual Data

All conversation messages are stored in the messages table in PostgreSQL, linked to individual conversation sessions recorded in the conversations table. Each message record stores the role (user or assistant), the text content, any associated image URL, and a timestamp. When a user continues an existing conversation, the backend retrieves the full message history and includes it in the context window sent to GPT-4o. This enables genuine multi-turn dialogue in which the assistant maintains full awareness of all design decisions, feedback, and refinements discussed throughout the session. For instance, if the user specified in message three that they dislike coloured tattoos, the assistant will continue to recommend monochrome designs in message fifteen without the user needing to repeat this constraint.

3. System Architecture

3.1 Architectural Overview

The Ink AI system follows a three-tier architecture. The presentation tier is a Next.js 16 frontend application using the App Router, TypeScript, and Tailwind CSS, served on port 3000. The application tier is a FastAPI Python backend using SQLAlchemy with asynchronous database sessions, served on port 8000. The data tier is a PostgreSQL 15 relational database. All three tiers are containerised and orchestrated using Docker Compose, ensuring consistent and reproducible deployment. External intelligence is provided by three Azure AI services accessed over HTTPS from the FastAPI backend.

The frontend communicates with the backend using two protocols. Standard HTTP/JSON is used for authentication, image uploads, image generation requests, and conversation management. Server-Sent Events (SSE) are used exclusively for the streaming chat response, enabling the assistant's reply tokens to appear in the interface in real time as they are generated by GPT-4o.

3.2 Detailed Data Flow

Step 1: User Authentication

Before interacting with the bot, the user registers or logs in through the authentication pages. The registration form sends a POST request to /api/auth/register with the user's name, email address, and password. The backend hashes the password using bcrypt and stores the user record in the users table. A JSON Web Token (JWT) is generated using the PyJWT library and returned to the frontend along with the user's profile data. The frontend stores this token in the browser's localStorage (under the Zustand persistence key) and in a session cookie, and attaches it as a Bearer token in the Authorization header of all subsequent API requests.

Step 2: User Input Capture

The user interacts with the system through the Next.js frontend at http://localhost:3000. Three input modalities are available within the same chat interface.

Text Input: The user types a message into the chat textarea component. The message is submitted either by pressing Enter or clicking the send button, both of which call the handleSend() function in the conversation page component.

Voice Input: The user clicks the microphone button, which mounts the VoiceInput.tsx component. This component requests microphone access from the browser using the navigator.mediaDevices.getUserMedia() Web API. Once permission is granted, it creates a MediaRecorder instance and begins capturing audio as a WebM-format audio blob. The user speaks their tattoo idea, then clicks the Stop button. The captured WebM audio blob is uploaded via HTTP POST to the /api/voice/transcribe backend endpoint with a Bearer token in the Authorization header. The backend service converts the WebM audio to a 16kHz mono WAV file using FFmpeg (installed in the Docker container) because the Azure Speech SDK requires WAV format input. The converted WAV file is passed to the Azure Speech Services recogniser. The resulting transcribed text is returned as a JSON response to the frontend, where it is automatically inserted into the chat input field. The user can review and edit the transcription before sending it as a message.

Image Input: The user can drag and drop an image file onto the chat input area or click the image attachment button to open the file picker. When an image file is selected, it is displayed as a thumbnail preview in the input area. When the user submits the message, the image file is first uploaded via HTTP POST to the /api/images/upload backend endpoint, which validates the file type (JPEG, PNG, WebP, or GIF) and file size (maximum 10 MB), saves the file to the /uploads/ directory with a UUID-based filename, and returns the server-relative URL. This persistent URL is attached to the outgoing chat message so the backend can locate the file on disk when constructing the vision message for GPT-4o.

Step 3: Conversation Initialisation

When the user sends their first message from the welcome page, the frontend first calls POST /api/chat/conversations to create a new conversation record in the database. The backend creates a row in the conversations table with a UUID primary key, the user's ID, and an auto-generated title based on the first message content. The returned conversation UUID is used as the URL parameter for all subsequent message requests in that session, and the page navigates to /chat/{conversation-id}.

Step 4: Backend Processing and Azure OpenAI Call

The frontend sends the user's message to POST /api/chat/conversations/{id}/messages. The FastAPI route handler performs the following sequence of operations. First, it saves the incoming user message to the messages table in PostgreSQL. Second, it calls the build_system_prompt() function in services/memory.py, which queries the user_preferences table for this user and constructs a dynamic system prompt incorporating their known preferences. Third, it retrieves the full message history for this conversation from the messages table. Fourth, it constructs the message array to be sent to GPT-4o. If the user's message included an image URL pointing to the /uploads/ directory, the backend reads the image file from disk, encodes it as a base64 data URI (for example, data:image/jpeg;base64,...), and constructs a vision-compatible message object containing both the text content and the image URL. This is required because the Azure OpenAI API is a remote service and cannot access the application's local file system directly. Fifth, it calls the Azure OpenAI GPT-4o deployment via the openai Python SDK with stream=True enabled.

Step 5: Streaming Response Delivery

The FastAPI route generates a streaming HTTP response using the SSE (Server-Sent Events) protocol. As GPT-4o generates its response token by token, each content delta is read from the async stream and immediately forwarded to the frontend as a JSON-formatted SSE event with the structure data: {"choices":[{"delta":{"content":"token"}}]}. The frontend's consumeSSE() function in lib/streaming.ts reads each event using the browser's fetch API with a ReadableStream reader, extracts the content delta, and appends it to the active assistant message in the Zustand chat store. The React component re-renders after each append, producing a real-time typing animation effect in the chat window.

Step 6: Generate Marker Detection and Concept Button

When GPT-4o determines — based on the accumulated conversation context and the behavioural rules in the system prompt — that sufficient information exists to generate a tattoo concept image, it embeds a structured marker at the end of its response. This marker takes the form [GENERATE: detailed image generation prompt here]. The marker contains a complete, detailed image generation prompt that GPT-4o composes from all conversation context, including the discussed style, elements, colours, placement, and any visual references from uploaded images.

After streaming is complete, the MessageBubble.tsx React component applies a regular expression (/\[GENERATE:\s*([^\]]+)\]/i) to the full response text. If the marker is found, it is stripped from the displayed text and a "Generate Concept" button is rendered below the assistant's message. The detailed prompt captured from inside the marker is stored as a prop on this button, ready to be submitted to the image generation endpoint when the user clicks it.

Step 7: Image Generation

When the user clicks the "Generate Concept" button, the GenerateButton.tsx component calls POST /api/images/generate with the AI-composed prompt and the current conversation ID. The backend's generate_tattoo_image() function in services/azure_image_gen.py applies a secondary enrichment step to the prompt, appending style-specific technical descriptors based on keyword detection (for example, if the word "japanese" is present, the suffix "Japanese irezumi style, bold outlines, traditional motifs, vibrant colour fills" is appended). The enriched prompt is then submitted to the Azure OpenAI gpt-image-1.5 deployment. The API returns a signed URL pointing to the generated 1024x1024 pixel image. The backend immediately downloads the image from this URL using the httpx HTTP client and saves it permanently to the /uploads/ directory with a UUID filename, because the Azure signed URL has a limited validity window. A record of the generation is saved to the generated_images table in PostgreSQL. The backend returns the permanent local image URL to the frontend. The frontend's GenerateButton.tsx component adds the image to the gallery store and also injects a new assistant message into the chat store containing only the image URL, so the generated concept image appears inline within the conversation thread immediately below the recommendation that prompted it.

Step 8: Preference Extraction Background Task

After the SSE stream closes and the assistant message is saved to the database, the FastAPI route triggers a background task using FastAPI's BackgroundTasks mechanism. This task calls GPT-4o at a temperature of 0 (deterministic output) with a structured extraction prompt requesting a JSON object containing four fields: preferred_styles, themes, color_prefs, and placement. The model is instructed to extract only preferences that the user explicitly expressed or strongly implied in the conversation. The update_preferences() function in services/memory.py then merges these new values into the existing user_preferences record for this user, deduplicating list entries and preserving all previously recorded preferences. This background extraction does not block the main response and is transparent to the user.

4. Azure AI Services: Technical Justification

4.1 Azure OpenAI GPT-4o (Chat and Vision)

Service: Azure OpenAI Service, GPT-4o deployment named gpt-4o, API version 2024-12-01-preview, hosted at https://tattoo-bot.openai.azure.com/

Purpose in the system: GPT-4o serves as the core intelligence of the recommendation system. It handles all user-facing conversation, interprets tattoo preferences expressed in natural language, analyses uploaded reference images through its native vision capability, generates detailed multi-point design recommendations, and composes the detailed image generation prompts that are passed to gpt-image-1.5.

Justification for Selection

Native multimodal vision support: GPT-4o natively processes both text and images within a single API call using a unified message format. When a user uploads a reference photo — for example, an existing tattoo, a piece of artwork, or a pattern they wish to incorporate — the backend encodes the image as a base64 data URI and includes it in the message payload using the vision-compatible content format: [{"type": "text", "text": "..."}, {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}]. GPT-4o then processes both the image and the text together, identifying the artistic style, specific visual elements, line weight, shading technique, and colour palette present in the image, and incorporating this analysis directly into its recommendation. This eliminates the need for a separate computer vision pipeline and keeps the architecture simple.

Instruction-following for complex, multi-constraint recommendations: Tattoo recommendation requires the model to simultaneously satisfy multiple creative and practical constraints. For example, a user may request a Japanese-style dragon that fits within a forearm sleeve, avoids the wrist area due to pain sensitivity, uses a muted colour palette with red accent eyes, and complements an existing geometric piece on the upper arm. GPT-4o's instruction-following capability reliably handles this level of compositional constraint, whereas smaller models tested in development produced generic or constraint-ignoring responses.

Real-time streaming API: The Azure OpenAI streaming API allows the backend to receive and immediately forward GPT-4o's response tokens to the frontend via Server-Sent Events. Each token is delivered within milliseconds of generation, so the user sees the response appearing naturally rather than waiting for the complete response. This streaming behaviour is critical for user experience in a conversational recommendation context, where responses may be several hundred words long.

Large context window: GPT-4o supports a 128,000-token context window. This is essential for the multi-turn conversational use case, as the full conversation history, user preferences, and system prompt must all be included in every API call. Conversations about complex tattoo designs can extend to thirty or more exchanges, and the model must retain awareness of all prior design decisions and user feedback throughout.

Implementation detail: The azure_openai.py service creates a singleton AsyncAzureOpenAI client with a custom httpx.Timeout of 90 seconds for reads (to accommodate longer responses) and max_retries=0 (to surface errors immediately rather than hiding them behind silent retries). The stream_chat_response() function constructs the full messages array, calls client.chat.completions.create(stream=True), and yields each choice.delta.content value as it arrives.

4.2 Azure OpenAI gpt-image-1.5 (Image Generation)

Service: Azure OpenAI Service, gpt-image-1.5 deployment, API version 2024-02-01, hosted at https://odlu-mnpspgf4-eastus2.cognitiveservices.azure.com/ (a separate Azure OpenAI resource from the chat model)

Purpose in the system: gpt-image-1.5 generates the visual tattoo concept images that appear inline in the chat conversation and are saved to the user's personal gallery. These images serve as the primary tangible output of the recommendation session, giving the user a visual reference they can present to a tattoo artist.

Justification for Selection

Availability on Azure as the current generation model: DALL-E 3, the previous generation image generation model on Azure OpenAI, was retired in March 2026 and is no longer available. The gpt-image-1.5 model is the current Azure-native replacement, making it the appropriate and only supported choice for image generation within the Azure ecosystem at the time of this project's development.

Prompt comprehension and artistic quality: The bot uses a two-stage prompt pipeline specifically designed to maximise the quality of generated tattoo concept images. In the first stage, GPT-4o itself composes a detailed, structured image generation prompt based on the entire conversation history. This prompt contains specific stylistic direction, subject matter, compositional guidance, colour palette information, and placement context. In the second stage, the backend's _enrich_prompt() function in azure_image_gen.py appends style-specific technical descriptors based on keyword detection — for example, if the word "japanese" appears in the prompt, the phrase "Japanese irezumi style, bold outlines, traditional motifs, vibrant colour fills. High quality tattoo design on white background." is appended. This two-stage enrichment ensures the generated image accurately reflects the specific artistic style discussed with the user.

Response format and persistence: The gpt-image-1.5 API with version 2024-02-01 returns a signed URL pointing to the generated image rather than a base64-encoded data string. Because signed URLs have a limited validity window, the backend immediately downloads the image using the httpx HTTP client and saves it as a PNG file in the /uploads/ directory with a UUID-based filename. This ensures the image remains permanently accessible through the application's static file server regardless of how much time passes after generation.

Implementation detail: A separate AsyncAzureOpenAI client instance is maintained for image generation (distinct from the chat client) because the two models require different API version strings. The image client is configured with a 120-second read timeout to accommodate the longer generation time typical of image models. The response_format parameter is deliberately omitted from the API call because gpt-image-1.5 rejects it as an unrecognised parameter, unlike its predecessors.

4.3 Azure Speech Services (Voice Transcription)

Service: Azure Cognitive Services Speech, Speech-to-Text, region eastus, endpoint https://eastus.api.cognitive.microsoft.com/

Purpose in the system: Azure Speech Services converts the user's recorded voice input into text, which is then treated identically to a typed message and passed to GPT-4o for recommendation processing. This provides a hands-free interaction option and makes the bot more accessible to users who prefer to speak rather than type.

Justification for Selection

Accuracy for domain-specific vocabulary: Azure Speech Services uses Microsoft's Unified Speech Model, which has been trained on a vast corpus of conversational speech and provides higher recognition accuracy than browser-native Web Speech API for specialist vocabulary. Tattoo consultations frequently involve style names (for example, "irezumi", "neo-traditional", "dotwork"), anatomical placement terms (for example, "sternum", "clavicle", "ditch"), and colour descriptors that general-purpose browser speech recognition may misrecognise. The Azure model handles this vocabulary with greater reliability.

Server-side processing for consistency: By processing audio on the server rather than in the browser, the application avoids the significant variability in speech recognition quality and language support across different browsers and operating systems. The browser's only role is audio capture via the MediaRecorder Web API, which records in WebM format. The backend then converts this WebM file to a 16kHz mono WAV file using FFmpeg before submission to the Azure Speech SDK, because the SDK requires WAV format with a specific sample rate. This conversion step is implemented in azure_speech.py using Python's subprocess module and runs in a thread pool executor to avoid blocking the async event loop.

Asynchronous SDK integration: The azure-cognitiveservices-speech Python SDK uses a callback-based event model. The implementation in azure_speech.py wraps these callbacks in an asyncio.Future that resolves when the recognized event fires or raises an exception when the canceled event fires. An asyncio.wait_for() call applies a 30-second timeout to prevent indefinite blocking. This pattern integrates cleanly with FastAPI's asynchronous request handling without requiring thread-blocking operations on the main event loop.

5. Recommendation Logic

5.1 System Prompt Architecture

The recommendation logic in Ink AI is implemented primarily through a carefully engineered and dynamically constructed system prompt that is rebuilt for every API call. The build_system_prompt() function in services/memory.py assembles this prompt from two components that together define the bot's persona, behavioural constraints, and user-specific context.

The base instruction component establishes the bot's identity and behavioural rules. It instructs GPT-4o to act as an expert tattoo artist and consultant working for Ink AI. It directs the model to discuss ideas, ask clarifying questions, and suggest styles before moving towards image generation. It specifies a set of numbered rules governing when and how to use the [GENERATE: ...] marker, including the requirement to ask the user's permission before generating any image and the requirement that the marker only appear when the user has confirmed they want to see a concept. This rule-based structure ensures the bot behaves predictably and does not generate unsolicited images.

The preference component is appended to the base instructions whenever the user's preference record in the database contains any entries. This section lists the user's known preferred styles, themes, and colour preferences, formatted as readable bullet points. For example, a user who has expressed interest in Japanese irezumi and fine line botanical styles in previous sessions will have a system prompt that begins with: "Known client preferences: Preferred styles: Japanese irezumi, fine line botanical. Themes: nature, lotus flowers, koi fish. Colours: soft pastels, black and grey." GPT-4o incorporates this context into every recommendation without the user needing to re-state their preferences.

5.2 Image Generation Gate

A critical aspect of the recommendation logic is the controlled gate that determines when an image generation prompt is offered to the user. The system prompt instructs GPT-4o to follow a strict two-step protocol. In the first step, the bot discusses ideas and refines the design concept through conversation. Once a sufficiently clear and specific design concept has emerged from the dialogue, the bot asks the user explicitly whether they would like to see a concept image. In the second step, if the user confirms (by saying "yes", "go ahead", "generate it", or a similar affirmation), the bot composes a detailed image generation prompt and embeds it in its response using the [GENERATE: ...] marker format.

The prompt inside the marker is composed by GPT-4o itself based on all context from the conversation. This prompt typically runs to two or three sentences and includes the specific style, subject matter, compositional details, colour palette, and background format. For example, a marker might contain: "A fine line botanical tattoo sleeve featuring lotus flowers, delicate vines, and lavender sprigs in soft pink, blue and green tones, flowing naturally along the arm contour from shoulder to wrist, detailed single-needle linework on a white background." This GPT-composed prompt is then further enriched by the backend's keyword-based enrichment function before being sent to gpt-image-1.5.

The frontend's MessageBubble.tsx component applies the regular expression /\[GENERATE:\s*([^\]]+)\]/i to the completed assistant message after streaming ends. If a match is found, the marker content is captured as the generation prompt, the marker itself is stripped from the displayed text (so the user sees only the readable recommendation text), and the "Generate Concept" button is rendered below the message containing the captured prompt as a component property.

5.3 Preference Extraction Loop

The preference extraction loop is the mechanism by which Ink AI accumulates knowledge about each individual user over time. It operates as follows. After every assistant message has been saved to the database, the FastAPI background task calls GPT-4o with a dedicated extraction prompt at a temperature setting of 0 to ensure deterministic, structured output. The extraction prompt instructs the model to analyse the full conversation and return a JSON object with four fields. The preferred_styles field is a list of specific tattoo styles the user expressed interest in. The themes field is a list of subject matter and motif preferences. The color_prefs field captures colour palette preferences. The placement field records body area preferences mentioned by the user.

The update_preferences() function in services/memory.py receives this JSON object and merges each list into the existing preference record for the user. New values are appended; existing values are preserved; duplicate entries are removed. The merged record is then written back to the user_preferences table. On the next message in any conversation, the updated preferences are retrieved and injected into the system prompt, so the bot's recommendations immediately reflect what it has learned.

This loop creates a compounding personalisation effect: each conversation refines the bot's model of the user's aesthetic preferences, making subsequent recommendations progressively more targeted and less generic. A user who has had three conversations with the bot will receive recommendations that draw on a rich accumulated profile, whereas a brand new user receives recommendations based on the general domain knowledge of GPT-4o's training corpus until the first extraction cycle completes.

5.4 Multi-turn Conversation Management

Each conversation in Ink AI maintains a complete message history that is retrieved from the database and included in every GPT-4o API call. The messages are ordered chronologically and formatted according to the OpenAI messages array format, with alternating user and assistant roles. The system prompt is always inserted as the first message with the role of "system". The full conversation is then appended in sequence. This approach, known as full-context prompting, allows GPT-4o to reference any detail from any point in the conversation when generating its response. The user can refer back to ideas mentioned earlier, ask the bot to compare two design options discussed in previous messages, or request modifications to a concept that was described several messages ago, and the bot will respond with full awareness of all prior context.

Conversations are stored persistently in PostgreSQL, meaning users can return to a conversation after days or weeks and the bot will resume with full awareness of what was discussed. The sidebar in the frontend displays the list of recent conversations retrieved from the /api/chat/conversations endpoint, allowing users to manage and navigate their conversation history.
